# Vibora AI setup

The Vibora chat in `vibora-littx.html` sends messages to `/api/ai/chat`. The
server keeps the provider key private, supplies the current published LITTX
event catalogue as grounding context, and returns matching live event cards.
The endpoint accepts an OpenAI-compatible Chat Completions API.

## Configure a model provider

Set these server environment variables in Vercel (or in
`staging/server/.env` for local development):

| Variable | Required | Purpose |
| --- | --- | --- |
| `LITTX_AI_API_KEY` | Usually | Secret key for the model provider. Keep it server-side. |
| `LITTX_AI_MODEL` | Yes | Model identifier supported by that provider. |
| `LITTX_AI_BASE_URL` | Only for a compatible/custom host | API root ending in `/v1`, for example `https://provider.example/v1`. When omitted, the server uses OpenAI's API root. |

For a self-hosted model with no API key, set both `LITTX_AI_BASE_URL` and
`LITTX_AI_MODEL`; the endpoint omits the Authorization header when the key is
empty. The host must be reachable from the LITTX server. `localhost` in a
Vercel function refers to that function, not a developer's computer.

The shared request limiter also needs the application's existing
`BOOKING_OTP_SECRET` or `SCANNER_SESSION_SECRET` (at least 32 characters) and
the configured database. This limits public AI usage to 15 requests per
five-minute window per IP. Requests and provider failures are bounded and the
server does not return provider error bodies or keys to the browser.

## About the supplied AI archives

`airi-0.14.1.zip` is a standalone multi-package app/runtime. `Open-LLM-VTuber-main.zip`
is a Python FastAPI/WebSocket voice-assistant runtime with audio and avatar
dependencies. Neither is a small website component that can run inside the
existing Vercel Node function: AIRI expects its own app/server stack, while
Open-LLM-VTuber's conversation interface is WebSocket-based and its runtime
expects a persistent Python process. The two projects also do not bundle a
ready-to-use hosted model credential.

LITTX therefore uses one small provider adapter in its existing Node API,
which is suitable for serverless deployment and can call any reachable
OpenAI-compatible model endpoint, including a separately hosted open model.
The two ZIPs remain intact as reference runtimes; their desktop clients,
audio stacks, avatar assets, and dependency trees are not copied into the
customer website. Direct, native connections to either runtime would require
a separately hosted service plus a protocol adapter. The backend response
currently provides text and event recommendations; voice synthesis and a
Live2D avatar are not part of this web integration.

Until a provider is configured, the chat reports that the AI is not connected
instead of pretending canned replies are generated by a model.
